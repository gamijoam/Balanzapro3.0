# Arquitectura y límites
- Organización > empresa > sucursal > almacén > ubicación; terminal, caja física y sesión son distintos. Identidad y ámbitos obligatorios en consultas y escritura.
- Individual: Flutter + Go + PG en PC; LAN: servidor central y clientes Flutter; nube: autoridad remota HTTPS; híbrido futuro: autoridad por sucursal, replicación de eventos hacia control central, sin dos escritores del mismo stock.
- Backend: módulos identity, permissions, organization, devices, module_registry, configuration, audit, inventory, currencies, costing, pricing, purchasing, sales, obligations, payments, treasury, fiscal. Domain → application → ports; adapters implementan puertos. No compartir tablas para escribir fuera del módulo propietario; unidad de trabajo coordina transacciones.
- Frontend: packages design_system, api_client, local_database, device_adapters; features por módulo; Riverpod candidato. UI adaptativa; no una pantalla idéntica en todos los tamaños.
- Módulos compilados estáticamente y activados por manifiesto (id, versión, deps, permisos, nav, settings, migrations). No cargar código no confiable ni borrar historia por desactivación. Licencia ≠ permiso ≠ activación: se deben satisfacer los tres.
- Configuración tipada versionada: global/organización/empresa/sucursal/terminal/usuario. Seguridad/fiscal no se pueden anular por preferencias.
## Consistencia y sincronización
POST de operación con UUID idempotente por empresa + tipo, hash de petición y resultado durable. Repetición idéntica devuelve resultado original; payload distinto es conflicto. SQL condicional UPDATE inventory_balances SET available=available-q WHERE ... AND available>=q RETURNING ... (esquema conceptual); locks en orden estable; rollback total; reintentar solo errores transitorios con límite. No asumir confirmación si timeout. Outbox dentro de transacción; publicación al menos una vez, consumidores idempotentes; cursor durable y resincronización completa. NOTIFY/WebSockets solo señal, no verdad durable. Versiones de catálogo, tasas y precios; cliente verifica continuidad. PowerSync candidato, no requisito.
- SQLite no autoridad: catálogo, precios, búsqueda FTS, carritos; sin servidor guardar borrador, no emitir/confirmar. Internet caído con LAN operativo no bloquea operación local, salvo servicios externos/fiscales. No replicar secretos ni costos a terminal sin permiso.
- Contratos: OpenAPI, identificadores UUID, decimales como texto, errores tipados + correlation_id, UTC y zona sucursal para fecha comercial, versiones compatibles. Propuestas de endpoints: POST /sales/checkout, GET /operations/{id}, GET /changes?cursor=..., POST /receipts, POST /payments. No son API implementada.
- Salida de datos: kardex y libro financiero inmutables; saldos materializados verificables. Archivos de producto/documento protegidos y referencias versionadas.
